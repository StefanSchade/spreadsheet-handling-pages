1. 0.2.2 — planned

Maintenance and consumer-driven capability release on top of v0.2.1. It consolidates the framework work since June 2026 and includes fixes and generic pipeline capabilities exercised by external consumers.

  • validate_references gained two consumer-neutral frame-contract rules. required_columns (frame, columns, optional exact: true) reports a missing frame, missing columns and, when exact, unexpected columns; column order is not part of the contract. non_empty (frame, columns, optional trimmed: true) reports every missing, null or empty-string cell, with trimmed also text that has leading or trailing whitespace, and honours when. Both follow the step’s mode and report through the existing finding shape, so a consumer no longer needs a local checker for table shape. Found by a consumer repository that had re-implemented them next to the pipeline.

  • Bug fix (BUG-JSON-INGRESS-MISSING-IDENTITY-P4A): JSON directory ingress now preserves Missing identity for explicit null values and structurally absent fields on supported pandas 2.x configurations instead of turning them into the literal strings "None" / "nan". Missing values normalize to the existing empty-string representation, while legitimate domain strings "None" and "nan" remain unchanged. The corrected behaviour is also verified against pandas 3.x.

  • Declarative primary_key / foreign_key validation and graph endpoint resolution now use category-aware relation-key identity. Strings compare exactly (including whitespace); Number/String and Boolean/Number pairs do not match; integral numeric carriers such as 1, 1.0, and numpy.int64(1) match; and Missing values never participate in relation resolution or primary-key duplicate identity. Graph unique_edges and reference unique_reference retain their existing generic tuple-uniqueness behavior. This is a bounded relation-key rule, not general scalar normalization.

  • Lookup enrichment, duplicate-key detection, and helper-mismatch verification now use category-aware relation-key identity. Strings compare exactly (including whitespace); Number/String and Boolean/Number pairs do not match; and integral numeric carriers such as 1, 1.0, and numpy.int64(1) match. Missing values never resolve or count as duplicate lookup keys, and mixed pandas key dtypes now follow Lookup’s configured missing-key policy instead of raising a pandas dtype error. This is a bounded Lookup rule, not general scalar normalization.

  • FK helper enrichment and validation now use category-aware relation-key identity: Strings compare exactly (including whitespace), Number/String and Boolean/Number pairs do not match, and integral numeric carriers such as 1, 1.0, and numpy.int64(1) match. Missing values never resolve or count as duplicate IDs; the literal String "nan" remains an ordinary duplicate-able key. This is a bounded FK rule, not general scalar normalization.

  • Workflow Coordinator prompts now include one mandatory, reviewed Coordinator-owned agent operating contract admitted before Run creation and recorded with bounded provenance in operator-plan evidence.

  • Workflow Coordinator repository policies now use the strict version 3 surface: consumer-owned evidence_commands definitions replace evidence_states and the former in-code command registry. Version 1 and 2 repository policies are rejected with a migration-required diagnostic; no backward-compatibility reader or migration machinery is provided.

  • Bug fix: FK validation no longer emits false unresolvable_fk or value_mismatch findings for Missing source FKs (None, "", NaN, pd.NA, or NaT). The literal string "nan" remains an ordinary FK value and is reported as unresolvable_fk when it does not resolve.

  • Opt-in less-trusted pipeline-description authorization (FTR-TRUSTED-INGRESS-P4A, Phase-E slice E7; implementation awaiting fresh independent review): trusted Python callers can supply a LessTrustedDescriptionAuthorization to build_steps_from_config, build_steps_from_yaml, or run_app. Its closed policy grammar grants exact registered step names, exact canonical plugin targets, and exact writer roots, with the resource-specific restrictions documented by the FTR. Omitting the keyword retains the existing trusted-description behavior, so current configurations require no migration. run_app applies E7 only while constructing AppConfig.pipeline; AppConfig.io remains trusted-operator- owned. Authorized plugins remain trusted same-process Python under their complete argument contract: this is not a Python sandbox. The initial sheets-run CLI does not advertise less-trusted YAML protection.

  • Asymmetric lookup join keys (FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2 Slice 1): add_lookup_helpers (enrich_lookup) gains an opt-in source_key/lookup_key parameter pair that joins a source-side key against a differently named lookup-side key (e.g. source story_id against lookup id). The pair is mutually exclusive with the symmetric key/keys/"on" forms and both halves are required together. Only the source key appears in the output frame; the lookup key never leaks, and helper_position: before_key anchors on the source key. All existing symmetric behaviour — values, columns, ordering, diagnostics, provenance, and errors — is unchanged; the asymmetric provenance additively records the distinct source_key/lookup_key instead of a synthetic common key. An explicit source_key/lookup_key pair is authoritative for join-key selection: it ignores a configured helper-policy key while still consuming the policy’s non-key settings (helper fields, allowed fields, order, missing behaviour, and helper value mode), and it keeps the asymmetric provenance shape even when the two key names are equal. A requested helper or temporary sort field that collides with the source key or the lookup key is rejected with a clear domain error before projection, so the source key is never overwritten and the lookup key never leaks in either values or formula mode. This collision safety follows the selected asymmetric mode even when the two key names are equal (an explicit asymmetric key cannot also be requested as a helper), while sorting the output by that key stays valid and legacy symmetric behaviour is unchanged. Requesting the same helper column twice is rejected with a clear domain error before projection (a generic guard for both modes) so output labels and helper provenance stay unambiguous. apply_derived_column_policy mismatch policies (warn_on_mismatch / fail_on_mismatch) now value-check asymmetric helpers by keying the payload on source_key and the lookup frame on lookup_key; they fail closed on invalid mismatch provenance. The join-key form is selected from mapping-member presence rather than value truthiness, so a present record with no key form, an explicitly null member, a partial, mixed, blank, or wrong-typed key all raise a clear error naming the metadata path; a named key column absent from the payload or lookup frame yields a severity-appropriate inability-to-verify finding instead of a silent pass; and policy: drop stays value-blind. This is a backend-neutral domain-lookup capability; it was subsequently bound across the persistence boundary, migrated into the worldbuilding pipelines, and used to retire project_by_role in the later slices recorded below.

  • Durable inbound helper binding (FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2 Slice 2): settles the public inbound sequence that lets apply_derived_column_policy(policy: drop) remove a read-only display helper (such as title) before the XRef inverse, using only existing steps (no new runtime capability). The durable carrier is _meta.sheets.<visible-sheet>.helper_columns written by configure_workbook_view; the transient _meta.derived provenance is pruned at the persistence boundary. Cleanup must run by the visible sheet name before apply_workbook_view_sheet_mappings, because that mapping re-keys frames but not _meta.sheets; logical-frame cleanup after mapping leaves the helper unclassified and the inverse would melt it. An edited read-only helper is discarded under value-blind drop, never melted or written back. The optional validate_references / no_helper_columns postcondition is declaration-bound: it and the cleanup read the same _meta.sheets.<visible-sheet>.helper_columns, so it catches an omitted or ineffective cleanup that leaves a declared helper behind, but it cannot detect a missing declaration (with no declaration both cleanup and guard see no helper and pass while the helper survives). A column name is never inferred; verifying that each Workbook View sheet declares its display helper is a consumer-owned static check (Slice 3 for the Worldbuilding matrix sheets). See the "Removing a read-only display helper before the inverse" section of the supporting-steps user guide.

  • Retired the project_by_role pipeline step (FTR-XREF-LOOKUP-HELPER-SUBSTITUTION-P4A2 Slice 4). Breaking public-step removal. After the Worldbuilding consumers migrated (Slice 3), the role-based projection step, its registration, its pipeline_step_registry.json and implementation_units.json records, and its four dedicated tests were removed. The read-only display-helper behaviour it provided is fully reproduced by the explicit lookup/helper composition: outbound add_lookup_helpers with helper_position: before_key, and inbound apply_derived_column_policy(policy: drop) bound to the durable _meta.sheets.<visible-sheet>.helper_columns carrier before the XRef inverse. There is no deprecated wrapper, alias, or hidden fallback; a pipeline still configuring step: project_by_role now fails with the normal unknown-step diagnostic. Migration: replace any project_by_role usage with the composition above (see Slice 1/2 entries and the supporting-steps user guide). The shared column-role resolver (spreadsheet_handling.domain.column_roles) and the foundation role taxonomy (row_identity, display_helper, matrix_value) are retained — they remain the source of truth for role-targeted add_validations.

  • Flat one-level XRef axis-label projection (FTR-XREF-AXIS-MAPPINGS-P4A2 Slice 2): two new opt-in pipeline steps, project_axis_labels (outbound) and restore_axis_keys (inbound), swap a relation’s axis-identity column (default column_key) between stable canonical keys and readable flat one-level visible labels, composed around unchanged contract_xref / expand_xref. The key/label bijection is resolved on every run from a live source frame (source_frame + key_column
    label_column) via the reviewed Slice 1 resolver; nothing is persisted, and an absent source frame fails rather than trusting stale or visible text. A canonical key missing from the mapping (outbound) or an unresolvable visible label (inbound) fails before any output is published; input frames and _meta are never mutated. Flat-string XLSX and ODS matrices round-trip with no carrier or XRef change. Hierarchical (tuple) labels and grouped multi-row headers remain later slices. Opt-in: existing flat XRef pipelines are unaffected.

  • Grouped XRef composites (FTR-XREF-AXIS-MAPPINGS-P4A2 GX-2): two new opt-in pipeline steps, contract_grouped_xref and expand_grouped_xref, project a canonical relation onto a grouped matrix whose dynamic column headers carry multi-level visible label tuples and restore it exactly, composing unchanged contract_xref / expand_xref with the reviewed grouped-header projection. The forward step publishes a GroupedMatrix — an internal domain carrier bundling the flat canonical matrix with its grouped-header descriptor; the inverse reads that carrier back. Raw carrier construction is rejected; the public grouped_matrix_from_canonical factory and the inverse both prove that the current canonical flat column schema projects to the exact carried descriptor, so reordered/moved/stale/altered headers fail before values can be assigned to different canonical keys. The arity-N key/tuple bijection is resolved on every run from a live source frame (source_frame + key_column + label_columns) via the Slice 1 resolver; nothing is persisted. xref_config_id selects the unchanged XRef metadata identity, while YAML name remains the pipeline step name. One-shot row_keys iterables are owned once and safely reused. Opt-in: existing flat and grouped-free XRef pipelines are unaffected.

  • Grouped XRef workbook carriers (FTR-XREF-AXIS-MAPPINGS-P4A2 GX-3b/GX-4): grouped matrices are now workbook carriers for both XLSX and ODS. A GroupedMatrix composes into an exact, lossless multi-row header grid (repeated literal labels, no reliance on merge geometry); reading it back with the opt-in configured-depth exact-header gate (exact_header_depths, per sheet, on the XLSX and ODS readers) yields a backend-neutral exact table that the new reconstruct_grouped_matrix pipeline step turns back into a validated GroupedMatrix under one live axis mapping, ready for the unchanged expand_grouped_xref. The exact read overrides merge-based header inference, captures every physical header cell verbatim (merged masters resolved, blanks preserved, no " / " join/split), and begins data directly below the configured depth. Opt-in: without the gate every read is byte-identical to before.

  • Grouped XRef workbook adoption through the public render path (FTR-XREF-AXIS-MAPPINGS-P4A2 GX-5): the already-accepted grouped workbook carrier is now reachable through the public configuration surface. An explicit configure_workbook_view sheet selection accepts a GroupedMatrix (preserved by identity) alongside ordinary DataFrames for inclusion, declaration order, and physical sheet rename; column-targeted sheet options (helper_columns, editable_columns, protection, generic options) are rejected for a grouped sheet because grouped identity is the full visible tuple. The router-facing save_xlsx / save_ods savers preserve a GroupedMatrix through to the render path instead of coercing it, while every other value keeps its existing DataFrame coercion. On readback, Workbook View sheet mapping now counts a core.ExactTable (produced under the exact_header_depths gate) as a projected visible sheet, so apply_workbook_view_sheet_mappings re-keys it to its logical frame for the unchanged reconstruct_grouped_matrix → expand_grouped_xref chain. A pre-render grouped Workbook View validation failure publishes no output file and mutates neither caller frames nor _meta. Opt-in: no new step, type, or parameter; existing DataFrame Workbook Views and direct backend writes are unchanged.

  • Legend Blocks canonical shape and resolved correction (FTR-LEGEND-BLOCKS-RESOLVED-SHAPE-CORRECTION-P5): meta.legend_blocks may still be authored as either a mapping or a list (list identity resolved from name, then id, then a positional legend<n> fallback), but list form is now normalized once to the canonical insertion-ordered mapping at an internal domain.ingress boundary invoked automatically after orchestrator load and after the bootstrap_meta / apply_overrides config merges. Every domain, validation, render, persistence, and carrier consumer now sees mapping form only. An explicit legend_blocks: null is treated as an absent declaration and canonicalized to an empty mapping, so structured persistence cannot emit a null Legend Blocks root. The render-derived resolved placement facet is Resolution, never durable Intent: it is stripped at domain ingress, at the structured sidecar persistence boundary, and — newly — from canonical XLSX/ODS workbook readback after the parser has used it to classify the legend surface, so it can no longer transiently re-enter canonical _meta. A default-placement legend that lands on its own sheet no longer round-trips as an extra payload frame (XLSX and ODS parity). Compatibility: external list and mapping authoring remain accepted through the application/config path, but direct low-level calls (run_pipeline, a raw render, or a backend save) with list-form legend_blocks are no longer supported — such callers must supply canonical mapping form or invoke ingress explicitly. Every configuration-derived callable string — the public plugin step, direct colon-style step: factories, and nested string targets accepted by generic frames-first or builder-style binders — passes through one pipeline-local ownership check before import and rejects the framework-internal spreadsheet_handling.domain.ingress namespace. Direct Python callable targets and ordinary dotted-callable plugins/factories are unchanged. The legend_blocks meta-registry entry now names its full producer/consumer surface. Entry-value semantics are unchanged and remain owned by FTR-LEGEND-BLOCKS-ENTRY-CONTRACT-P5.

  • Compact Multiaxis persistence correction: composed expand/contract runs no longer persist XRef metadata that names their deleted internal temporary relation. A legitimate caller-supplied prior XRef entry is restored exactly. _meta.compact_multiaxis remains persisted as a diagnostics-only trace; it is not inverse intent or configuration fallback, and it no longer blocks column schema maintenance. Sparse Defaults remains a separate explicit pipeline composition.

  • Compact Multiaxis scoped recomposition (FTR-COMPACT-MULTIAXIS-SCOPED-RECOMPOSITION-P4A): expand_compact_multiaxis gains an optional base_canonical_relation parameter so a partial spreadsheet projection (a matrix and/or value_columns that expose only a subset of a larger relation) can be reimported without losing rows outside the visible scope. The composite Cell-Codec-encodes the named canonical base relation to the compact relation shape XRef expects, passes it through the wrapped expand_xref as its base_relation (in-scope matrix addresses replace — or, when cleared, delete — exactly the visible scope; out-of-scope base rows are preserved), then decodes the merged result. No parallel merge logic is added; replacement, deletion, and ordering stay XRef-owned. The parameter is opt-in and names the pre-codec canonical shape, distinct from the compact-shaped expand_xref base_relation; omitting it reproduces the previous full-replacement behavior, so existing full-matrix pipelines are unaffected. The intermediate encoded base is an internal temporary frame that never leaks into returned or persisted metadata.

  • Carrier-neutral final domain cleanup (FTR-META-ONTOLOGY-REMOVAL-WORKBOOK-PROJECTION-EPIC-P4A, first slice): pipelines can now remove redundant logical frames before persistence so that every output adapter — JSON/YAML/XML/CSV directories and XLSX/ODS workbooks — observes the same cleaned frame set. A new configure_pipeline_cleanup step declares either drop_frames (frames to remove) or keep_frames (final frame set to retain; mutually exclusive modes, contradictions fail). expand_xref / contract_xref gain an explicit drop_source parameter that marks the superseded source frame for cleanup. The orchestrator executes and consumes these commands implicitly between the configured steps and the persistence boundary; commands never persist or roundtrip. A frame targeted by an explicit drop command while explicitly mapped by workbook_view fails before anything is written. Known limitation: artifacts written by mid-pipeline steps (write_structured_yaml, write_key_value_resources) are emitted before the cleanup boundary and reflect the earlier uncleaned state.

  • Cleanup/Workbook-View conflict refinement: only explicitly drop-commanded frames conflict with an explicit workbook_view mapping. Keep-mode implied removals coexist with (possibly reimported, stale) view mappings, so reverse pipelines can retain a canonical frame subset from a workbook whose persisted view still maps the discarded view frames; the spreadsheet renderer still fails loudly if such a workbook were written again with a mapped frame missing.

  • _meta.workbook_view.sheet_mappings entries are now frame-only (sheet + frame). The derived canonical_frame key is no longer produced; legacy persisted mappings that carry it are ignored on read. Schema maintenance (sheets-schema-maintain) now routes sheet-scoped column references to the frame actually mapped to the sheet (frame-only resolution): renaming a column of a projection’s source frame no longer updates constraints or sheet options that target the projection’s sheet. The projection/source relationship remains feature-local transformation knowledge (for example xref_crosstable intent), not generic mapping identity.

  • Generic frame lifecycle/render ontology has been removed. Rendering now selects every remaining logical frame when no explicit workbook_view.sheets list exists; an explicit list is authoritative for selection, names, and order. configure_workbook_view no longer accepts or writes lifecycle/render-policy knobs (mode, drop_redundant_data, unknown_frame_policy, debug/role inclusion controls, or sheet lifecycle fields). Generic lifecycle writes were removed from extraction, join, pivot, compact-multiaxis, lookup-enrichment, and Workbook View producers; legacy frame_lifecycle payloads are ignored and stripped at persistence. Schema maintenance no longer treats canonical_frame as a generic frame reference. Feature-local inverse contracts and FK relation produced_by conflict identity remain unchanged.

  • XRef projection family (expand_xref / contract_xref): persisted _meta.xref_crosstable entries now carry only the minimal inverse intent (relation, matrix, row_keys, dense_axes intent); the descriptive operation, column_key, value, and drop_empty fields are no longer written (legacy payloads are tolerated). Intent lookup by frame name now fails explicitly when multiple entries match instead of silently using the first — in the transformations, in sparse-default targeting, and in column-role resolution (pass explicit key_columns to disambiguate). drop_source now rejects checkable value loss: a contraction over a relation with fields beyond row_keys + column_key + value, a contraction whose matrix columns do not cover every relation column key, or an expansion whose explicit value_columns leave matrix columns unexpanded. XRef roundtrip matrix-axis identities are now contractually unique, non-empty strings (carrier-stable across XLSX/ODS headers): numeric, missing, mixed-type, duplicate, or unhashable axis identities fail with explicit diagnostics on every axis-identity source — relation column_key values, explicit/metadata-derived/dense-derived column_keys, scoped base_relation identities, and the full physical matrix header row — before any cleanup command is recorded; explicit value_columns are validated as axis identities before the row_keys overlap check, so a missing (pd.NA), numeric, or array-valued selector now yields the XRef diagnostic instead of a raw pandas/NumPy error. Physical relation/base_relation column labels are a distinct, weaker boundary — non-missing, hashable, uniquely and deterministically comparable, and scalar-addressable, but not required to be strings: missing-like (None/NaN/pd.NA), ambiguous-equality, unhashable (for example a Python list), or duplicate physical labels are rejected before any output or cleanup (closing a case where duplicate NaN/pd.NA labels previously produced a Series cell and an unwanted cleanup command, and a deterministic unhashable label previously raised a raw TypeError inside pandas membership). Duplicate configured row_keys and value_columns overlapping row_keys fail the same way. Typed (non-string) matrix-axis identities were never carrier-stable and are explicitly unsupported; hierarchical/tuple physical labels remain future design work, neither promised across the operation surface nor prohibited by a global string-only rule. sheets-schema-maintain handles _meta.xref_crosstable with a dedicated checker that blocks renames/drops only for real XRef references (row_keys on the relation/matrix frames, matrix column_keys including stored dense_axes.resolved.column_keys snapshots, dense-axis keys); convention-style shapes inside the root no longer block, and real references no longer dangle silently.

  • Cell Codec projection family (encode_cell_values / decode_cell_values): codec intent lives entirely in explicit step configuration; the _meta.cell_codecs family is retired (it had no runtime reader — legacy payloads in old sidecars/workbooks are ignored pass-through sediment, and sheets-schema-maintain no longer blocks on them). The string-oriented contract is enforced on the position-based path: numeric/boolean/date participating values fail explicitly instead of silently changing type; empty and missing values encode as the configured absent_value and decode to "". Declaration guards reject duplicate participating/group columns, duplicate physical labels, compact-column collisions, absent_value containing the separator, and decode collisions with existing columns. split_tokens serialization now rejects tokens containing the delimiter (previously producing cells that could not be decoded back to the same tokens). The user-guide section was corrected (actual modes are whole_cell_code / split_tokens with delimiter default -; the position-based codec_intent contract is now documented).

  • sheets-schema-maintain now maintains lookup-helper policy references in _meta.helper_policies.lookup: renaming a column of the lookup frame updates the policy’s key, allowed_helpers, default_helpers, and order.sort_by references, and dropping a column referenced by a lookup policy is blocked (prune included). Previously these references silently dangled after a rename or drop.

  • sheets-schema-maintain no longer silently ignores unmaintained _meta.helper_policies subtrees (anything other than fk and lookup): if such a subtree contains a structured frame+column reference to the affected column, rename/drop now blocks with a reported metadata reference instead of leaving the reference dangling.

  • Bug fix (BUG-ODS-XLOOKUP-FORMULA-INTEROP-P4A): ODS formula-mode FK-helper and lookup-helper formulas (helper_value_mode: formula) previously opened as #NAME? in LibreOffice Calc even though the lookup references were valid, until each formula was manually reparsed through the Function Wizard. The ODS writer now serializes the lookup as LibreOffice’s extension-qualified COM.MICROSOFT.XLOOKUP rather than plain XLOOKUP (not part of the standard OpenFormula vocabulary), so generated formulas evaluate immediately — verified against LibreOffice 25.2.3.2, including live recalculation on a source FK edit and the configured missing-result behavior for an unknown key. XLSX formula rendering and both backends' helper_value_mode: values are unchanged. values remains the broader-compatibility fallback for LibreOffice versions without XLOOKUP support, but it does not update the displayed helper value live when the source FK is edited.

  • Bug fix (BUG-ODS-MISSING-CARRIER-LITERAL-NAN-RENDERING-P4A): the ODS writer’s per-cell emptiness check was NaN-blind, so a real pandas/NumPy missing value reaching the renderer — e.g. a successful FK-helper lookup whose resolved target field is itself missing, or an ordinary blank cell loaded from a csv_dir source — was serialized as the literal text "nan" instead of an empty cell. Both cases now render (and reimport) as an empty cell on ODS, matching XLSX’s existing behavior. A legitimate domain value that is literally the string "nan" is unaffected and still round-trips as "nan".

  • Bug fix (FTR-MINIMAL-INTERNAL-VALUE-MODEL-P4A Slice 1, D2): the csv_dir directory-read ingress path applied pandas' default dtype inference and NaN handling instead of the string-preserving contract already used by the single-file CSV path, JSON, and YAML. A blank cell now loads as "" rather than a pandas NaN, and a numeric-looking textual value such as "007" is no longer dtype-promoted to a number — it retains its exact textual representation, matching the already- established csv_dir/CSV/JSON/YAML ingress contract for every other format. This is the matching ingress-side fix for the same carrier-leak class the BUG-ODS-MISSING-CARRIER-LITERAL-NAN-RENDERING-P4A renderer- side fix above closes.

  • Bug fix / new capability (FTR-DATE-TIME-INTERNAL-VALUE-MODEL-P4A D-T2): save_yaml_dir (yaml_dir output) and write_json_dir/JSONBackend.write_multi (json_dir output) previously raised yaml.representer.RepresenterError or TypeError for any datetime.date/datetime.datetime/pandas.Timestamp cell value, including a column loaded unmodified from a YAML file’s own native timestamp tags. Both now accept these values: YAML writes a native, unquoted date/timestamp scalar at microsecond precision (a missing temporal cell writes as null, matching the existing datetime.date convention); JSON writes reserved, single-key {"$date": "<ISO date>"} / {"$datetime": "<ISO datetime, offset suffix iff aware>"} envelopes at microsecond precision (a missing temporal cell writes as "", matching every other column’s existing Missing convention). Timezone awareness and the exact numeric UTC offset are preserved; named/IANA timezone identity and pandas.Timestamp-vs-datetime.datetime carrier identity are not. read_json_dir/JSONBackend.read_multi is deliberately unchanged for this slice: a $date/$datetime envelope written by write_json_dir reads back as a plain string, not a native temporal value.

  • Breaking change (FTR-XREF-PHYSICAL-LABEL-METADATA-AUTHORITY-P4A): contract_xref/expand_xref’s `row_keys and dense-axis rows_from/columns_from key/keys selectors — including the inherited Compact Multiaxis forwarding trace — must now be an exact, non-empty native str (type(value) is str and value != ""; no coercion or stringification). This retires the previously published or mechanically-accepted non-string selector (numeric, boolean, date/datetime, NumPy/pandas scalar variants, bytes, complex, frozenset, a stable custom hashable/comparable object, a str subclass, or numpy.str_) for this specific nominated-selector role only: only a str physical column label reloads under the identical name on every currently maintained frame-plus-metadata carrier (JSON directory, XLSX, ODS). A numeric selector, for example, previously worked in-process but silently broke a later lookup after any of these carrier round trips, because the referenced physical column itself retypes on reload even though the persisted metadata copy does not. Non-string physical DataFrame columns remain fully legal everywhere they are not nominated as a row_keys/dense-axis selector (the general physical-label contract is unchanged); whitespace-only string selectors remain accepted.

  • New capability / breaking change (FTR-TRUSTED-INGRESS-P4A, Phase-E slice E3 — metadata substrate admission): every maintained external-to-Domain _meta boundary (initial framework ingress, bootstrap_meta, apply_overrides) now enforces a bounded metadata substrate grammar after Legend Blocks' own shape normalization: _meta is either absent/None, or an exact dict whose recursive ordinary containers are exact dict/list, whose dict keys are exact str with no exceptions, and whose leaves are an E1-admitted ordinary Scalar (string, boolean, number, date, datetime, or a recognized missing carrier). A shared acyclic alias (the same nested object reachable from two independent branches) is permitted; a self- or indirect cycle is rejected. Legend Blocks' complete normalized output is checked by this same walker, so an out-of-grammar node cannot escape by virtue of coming from a delegate. Rejection is atomic and non-mutating: a violation anywhere in the tree leaves the caller’s _meta object graph completely unchanged and aborts before any pipeline step, cleanup, or saver runs.

    Two carrier-reachable but never-semantically-supported shapes are narrowed as part of this slice, both previously silently tolerated by the retained legacy-read paths with no prior compatibility disposition:

    • YAML directory metadata sidecar (Option A). In a yaml_dir input, the file stem _meta is now reserved for framework metadata: at most one of _meta.yaml/_meta.yml may be present, it is safe-loaded and must be a mapping at its root, and it is placed directly at Frames["_meta"] — never materialized as an ordinary DataFrame sheet. Both spellings present, or a non-mapping (including empty-file) root, is rejected at the YAML backend/parse boundary with a clear error. Migration: a yaml_dir input that used _meta.yaml/_meta.yml as an ordinary data sheet (it was never a supported roundtrip contract — the existing YAML saver already skips writing a _meta sheet) must rename that file; a yaml_dir input that intends framework metadata must supply a plain mapping. The YAML saver continues to omit _meta on write; no new roundtrip promise is added.

    • Legacy Python-literal and YAML-tag special metadata values/keys. The legacy XLSX/ODS workbook_meta_blob ast.literal_eval fallback, and YAML’s !!set/!!binary tags reachable from an authored or structured _meta.yaml sidecar, can produce a tuple, set, bytes, or complex metadata value, or a non-str (int/bool/float/None/tuple) dictionary key. The legacy/YAML carrier parse itself is unchanged and still recovers the surrounding dict; E3 now deterministically rejects the specific unsupported node at its exact metadata path, with a safe diagnostic that never renders the rejected value or key. None of these shapes is silently coerced (no str()/list() conversion) or silently admitted. Migration: a workbook or metadata sidecar carrying one of these legacy/tagged shapes must be rewritten with an application-specific, meaning-aware replacement (e.g. a set as a list) before it can be re-ingested; ordinary metadata already limited to dict/list/str-key/ Scalar shapes is unaffected.

    No existing maintained producer/consumer needed a compatibility exception: current XRef dense-axis metadata (row_keys, dense_axes key/keys, resolved.row_identities, and the Compact Multiaxis-forwarded row_keys copy) was already narrowed to exact non-empty str selectors by the independently accepted FTR-XREF-PHYSICAL-LABEL-METADATA-AUTHORITY-P4A (noted above) and passes this new substrate check unchanged, with no XRef-specific E3 exception. Family-level metadata semantics (Legend Blocks entry validity, XRef business rules, workbook-view shapes, and so on) remain exactly as validated by their own owning features; E3 only enforces the structural substrate, not per-family meaning.

  • Behavior change (FTR-TRUSTED-INGRESS-P4A, Phase-E slice E4 — R1 finding scalarization): validate_references and validate_graph’s warn-mode finding reports now emit only a Scalar-compatible `row_index cell, unconditionally. A pandas.MultiIndex row index becomes a comma-joined diagnostic String (e.g. "east, 1") instead of a raw Python tuple object. Any other row-index label that is neither an admitted Scalar carrier nor a MultiIndex tuple (reachable today because no row-index grammar is yet selected for arbitrary hashable DataFrame indexes) is replaced by the stable placeholder String "<unsupported row index>" rather than reaching the report cell as a raw object. An ordinary (default integer-indexed) row_index is unchanged and is not stringified. Migration: any consumer that inspected row_index on a finding and relied on it being a Python tuple, or on it being the original raw index object for a non-default index, must switch to parsing the String label instead; none of this was ever a documented contract, and the label is a diagnostic projection, not a reversible codec.

  • New capability / breaking change (FTR-TRUSTED-INGRESS-P4A, Phase-E slice E5 — framework-managed macro wiring): the single macro seam every router-backed entry point funnels through (orchestrate, and therefore sheets-run, run_app, the compatibility orchestrator shim, sheets-schema-maintain/run_schema_maintenance) now enforces the complete Trusted Ingress E1-E4 contract end to end, rather than only the metadata-substrate slice (E3) it already enforced. Two user-visible consequences:

    • Initial ordinary structural/Scalar admission is now wired in. A router- loaded top-level carrier that is not an ordinary DataFrame/ExactTable (e.g. a raw non-tabular value under a non-_meta key), a DataFrame whose physical columns fail the existing addressability contract, or any ordinary cell that is not one of the six admitted Scalar categories, is now rejected before the first configured step runs — previously this E1/E2 representation existed but was not reachable from the macro. Migration: none for conformant input; a payload that only worked because this check was unreachable must be corrected at the source.

    • A configured step’s returned candidate is now conservatively re-established when it is not an exact reviewed transition. Every step is classified against the closed, exact E4 transition set (the add_lookup_helpers(helper_value_mode="formula") FormulaSpec introduction, contract_grouped_xref/reconstruct_grouped_matrix GroupedMatrix introduction, their one admitted nested composition, both expand_grouped_xref reverse endpoints, and write_artifact_manifest’s manifest role). A step outside that exact set — any built-in without an exact certificate, dotted-plugin step, or caller-supplied `BoundStep, regardless of what it wraps — has its returned candidate pass ordinary re-establishment before the next step, final cleanup, or save; a candidate that cannot become ordinary (a surviving FormulaSpec, GroupedMatrix, or non-Scalar manifest cell) now raises before any later Domain processing or save runs. At final save, a GroupedMatrix/ LookupFormulaSpec role may reach only an xlsx/ods output kind and the artifact-manifest source_frames role may reach a save only after whole-frame _meta.pipeline_cleanup removal of its frame; any other combination now raises application.managed_pipeline.UnauthorizedControlledRoleAtSinkError before the saver runs, instead of reaching an incapable adapter. Migration: a pipeline that relied on a non-formula-mode helper, a grouped/manifest role surviving to an unsupported output kind, or any other previously-unenforced uncertified-return shape must either drop the artifact manifest’s source frame via configure_pipeline_cleanup before save, target a FormulaSpec-capable sink (xlsx/ods), or otherwise ensure every configured step’s return is ordinary before it reaches the saver; the maintained FormulaHelper → GroupedMatrix → XLSX/ODS path and every other currently maintained flow are unaffected.

    run_pipeline itself remains unchanged and unwired: a caller invoking it directly (bypassing orchestrate) still receives no automatic ingress or re-establishment, exactly as before.

  • Safety/correctness narrowing — FK helper / DCP deletion authority (Derived Artifact / FK Helper Deletion Authority workstream): durable FK relation policy (_meta.helper_policies.fk) alone no longer authorizes physical deletion of an FK-attributed helper column, in either remove_fk_helpers or apply_derived_column_policy. Previously, a durable relation that merely named a column as a potential FK helper could cause that column to be dropped even without current evidence that this pipeline run actually produced it — risking deletion of a same-label foreign column a durable relation happened to also name. Deletion now requires current, truthful transient producer provenance (_meta.derived.sheets.*.helper_columns), unless another independently accepted deletion authority applies. Migration consequence: generic persistence prunes transient _meta.derived provenance at the persistence boundary, so after a reimport with no fresh helper-materialization pass in the same session, a durable FK relation that still names a helper column can no longer cause it to be dropped; the column survives with a non-raising diagnostic. The supported durable cleanup route for this case remains explicit Workbook-View _meta.sheets[*].helper_columns declaration (via configure_workbook_view), which a pipeline author declares deliberately and which is unaffected by this narrowing.

  • Bug fixes — apply_derived_column_policy mismatch checking for enrich_lookup helpers (FK / Reference-Helper Domain-family hardening, F-002 Slice 2): two intentional, user-observable corrections to warn_on_mismatch/fail_on_mismatch.

    • Formula-mode helper mismatch checking is now correct. Previously, a helper_value_mode="formula" helper cell (a LookupFormulaSpec, not a copied scalar) was compared via str(LookupFormulaSpec) against the plain canonical lookup value — this essentially always mismatched, spuriously reporting derived_value_mismatch under warn_on_mismatch and always raising under fail_on_mismatch, for every correctly-enriched formula-mode row. Formula-mode cells are now compared structurally: the cell’s declared (lookup_sheet, source_key_column, lookup_key_column, lookup_value_column) identity against the relationship the provenance declares. A structural divergence is now reported under a new rule_type, derived_formula_mismatch, distinct from derived_value_mismatch; a structurally-correct formula cell now produces no finding. This combination never worked correctly before, so there is no valid prior state to preserve; treated as an explicit, evidenced bug fix, not a claim of zero compatibility risk. Comparison is per-cell (by the cell’s own runtime type), so a formula-mode column with one row manually overwritten by a literal value is checked as a scalar edit on that row alone. A multi-key symmetric enrich_lookup (keys: […​] with more than one key) combined with a formula-mode helper cannot be structurally verified by the current single-key LookupFormulaSpec representation (a pre-existing, unrelated enrich_lookup write-path characteristic, unchanged by this fix) and is now reported as unverifiable_enrich_lookup rather than silently certified as structurally correct or incorrectly flagged.

    • Duplicate lookup keys are no longer silently tolerated. Previously, if the current lookup frame had duplicate rows on the join key(s) at mismatch-check time, apply_derived_column_policy picked the first matching row as canonical ("first occurrence wins") and certified mismatch results from it — an unowned tie-break with no counterpart in enrich_lookup’s own contract, which instead rejects duplicate lookup keys outright at enrichment time. Duplicate lookup keys at mismatch-check time are now reported as `unverifiable_enrich_lookup (a warning under warn_on_mismatch, a failure under fail_on_mismatch) instead of silently certifying a value from an arbitrary row. Migration: a pipeline that relied on the previous silent pass for a lookup frame that had gained duplicate keys after enrichment time now receives a finding (or a raise under fail_on_mismatch) instead; deduplicate the lookup frame, or reconcile provenance, before the mismatch-check step.

2. 0.2.1 (released)

These notes describe the 0.2.1 release line on top of v0.2.0. The release is intended as a stable foothold before the planned contract-first domain/meta reset around a Functional-Model-derived bridge DSL. It preserves the current working runtime surface, captures the Functional Model catch-up work, and records the architectural decision that future domain/meta changes may intentionally break historical internals when doing so reduces sediment.

0.2.1 remains pre-1.0 software. It is not a long-term compatibility promise. Its purpose is to provide an installable PyPI anchor before larger internal domain/meta changes begin.

2.1. Functional Model, Project Memory, and reset direction

  • The Functional Model was extended from requirement-inquiry material rather than from implementation details alone. New or updated use-case concepts cover Cell Codec, Compact Multiaxis, Sparse Defaults, derived frame views, validation use cases, header shape projection, hierarchical config projection, aggregate/pivot reconciliation, workbook-view boundary behavior, and XRef/discriminator composition.

  • The repository-wide June-2026 transformation/capability family inventory was archived in cold storage and linked from Project Memory as the canonical reference for implemented capability families and Functional Model coverage status. The inventory remains evidence material, not a backlog or second source of truth.

  • Future requirement inquiries were preserved for later work, including nested structures, typed cell values, conditional follow-up table views, and multi-row header presentation. These are recorded as future concepts, not as implemented 0.2.1 runtime capabilities.

  • ADR-CONTRACT-FIRST-DOMAIN-META-REWRITE accepts a contract-first domain/meta reset around a stabilized bridge DSL. The ADR explicitly frames the domain/IO seam as a shared Frames + Meta language whose writer, reader, lifecycle, conflict, and deletion rules should be derived from Functional Model use cases. It preserves adapter/parser/renderer knowledge, allows targeted deletion of obvious duplicate paths, and rejects recreating the current registry-scale surface under new names.

  • Project Memory now records the bridge-DSL reset as a high-weight Domain/Meta steering decision. This is intended to counterbalance overly conservative readings of the existing documentation: low external adoption makes bounded breaking changes acceptable when they reduce historical implementation sediment.

2.2. Spreadsheet backends and roundtrip behavior

  • User-authored text orientation (vertical / rotated cells) is preserved through XLSX roundtrips under the text_orientations presentation metadata key. ODS roundtrips also preserve text orientation: style:rotation-angle is written on style:table-cell-properties, the carrier ODF defines for cell text rotation, so the rotation is honoured by external consumers such as LibreOffice Calc rather than only by the project’s own parser.

  • ODS column widths are preserved across render/parse via style:table-column-properties with an approximate Excel-character / cm conversion. The conversion is documented as approximate; widths authored by external ODS producers may not round-trip with byte-exact XLSX parity.

  • The ODS presentation-metadata extractors (column widths, text orientations) share the grid parser’s defense against sheet-wide LibreOffice formatting fillers: extraction is clipped to the parsed content extent so that a number-rows-repeated / number-columns-repeated filler carrying a rotation or column-width style cannot materialize one metadata entry per implied address, and the same ParserLimits are honoured on per-axis and per-cell bases as defense-in-depth.

  • User-authored horizontal cell alignment is preserved through XLSX and ODS roundtrips under the horizontal_alignments presentation metadata key. Canonical vocabulary is intentionally narrow in this slice — only left, center, and right are recognised; XLSX general / fill / justify / distributed / centerContinuous are dropped on read and never emitted on write. The ODS write path emits fo:text-align on style:paragraph-properties (the ODF-defined carrier for cell text alignment); the read path accepts both absolute (left / right) and locale-neutral (start / end) forms and normalises to the canonical absolute encoding so re-imports under different locales remain stable.

  • The XLSX renderer now merges alignment attributes when more than one render op touches cell.alignment (currently SetTextOrientation and SetHorizontalAlignment). Existing rotation behaviour is unchanged when no other alignment op is present; cells that combine rotation and horizontal alignment now retain both attributes regardless of op-dispatch order.

  • The ODS horizontal-alignment extractor inherits the same content-extent clipping and ParserLimits enforcement as the existing text-orientation and column-width extractors, so a sheet-wide "select all + left-align" filler cannot materialise one metadata entry per implied address.

  • The presentation-metadata families column_widths, text_orientations, and horizontal_alignments now share a single replace-or-clear policy on parse: parsed carrier state is authoritative for the sheet-local entry, and clearing the visible carrier removes any persisted entry for that sheet so the next roundtrip cannot silently reapply formatting the user has removed. Previously this behaviour was implemented only for horizontal_alignments; text_orientations and column_widths retained merge-only semantics and could surface stale embedded metadata after a cleared visible carrier. Behavioural note for column_widths: removing a custom column width from the visible carrier now removes the embedded entry as well, where previously the entry persisted. This is a deliberate alignment of behaviour across the three families and matches user intent ("I cleared this; do not reapply it").

  • User-authored vertical cell alignment is preserved through XLSX and ODS roundtrips under the vertical_alignments presentation metadata key. Canonical vocabulary is intentionally narrow in this slice — only top, center, and bottom are recognised; XLSX justify / distributed and ODS automatic are dropped on read and never emitted on write. The ODS write path emits style:vertical-align on style:table-cell-properties (the ODF-defined carrier for cell vertical alignment) and applies the intrinsic ODF ↔ OOXML vocabulary remap — canonical center serialises as ODF middle on write and ODF middle normalises to canonical center on read — so cross-backend roundtrips stay stable. The new family joins column_widths / text_orientations / horizontal_alignments under the same authoritative-carrier semantics.

  • The hidden XLSX / ODS _meta carrier now roundtrips the canonical workbook meta as one coherent mapping even when a sheet-level representation accidentally leaks into the writer or a malformed file carries a nested workbook_meta_blob wrapper. The carrier-local helper field workbook_meta_blob is recognised as a hidden-sheet convention only, so it can no longer shadow or structurally replace _meta.workbook_view during readback. This restores XLSX workbook-view readback parity with ODS for declarative project_by_role pipelines. See BUG-XLSX-WORKBOOK-VIEW-BLOB-READBACK-P4A.

  • As a follow-up hardening, canonicalize_workbook_meta now strips the sheet-level export marker keys (author, exported_at, version) from canonical workbook meta whenever they carry the MetaPass-default empty signature (None / empty string). They describe the hidden _meta sheet itself, not the canonical workbook meta contract. Without the strip, a corrupt or empty inner blob would leave the outer wrapper visible as if it were canonical content, hiding the absence of workbook_view behind wrapper noise (the post-e939623 residual symptom). Marker keys with caller-assigned non-empty values still round-trip unchanged. See BUG-XLSX-WORKBOOK-VIEW-CANONICAL-META-LOSS-P4A.

  • The persistence boundary now applies a narrow Intent-vs-Resolution rule for the cross-carrier _meta sidecar failure observed in the worldbuilding consumer. Persisted meta keeps declarative intent, but drops three reconstructible resolution facets from the captured ODS-produced sidecar: legend_blocks[].resolved, xref_crosstable[].dense_axes.resolved, and xref_crosstable[*].column_keys. This prevents backend-produced resolved layout / axis snapshots from poisoning later XLSX workbook-view readback while leaving broader lifecycle classification to the existing metadata follow-up FTRs. See BUG-CROSS-CARRIER-META-ROUNDTRIP-P4A.

2.3. Pipeline steps and role-based projection

  • New pipeline step project_by_role reorders / retains a projected frame’s columns by foundation column-role (row_identity, display_helper, matrix_value). direction: is required (outbound retains all three roles; inbound drops display_helper); there is no silent default. Optional role_order: permutes the per-direction default order; including display_helper in an inbound role_order is a validation error. Optional helper_columns: and key_columns: are interim per-call-site overrides that win over scattered upstream sources. See FTR-DYNAMIC-FRAME-PROJECTION-IMPL-P5.

  • Role classification is consumed from the foundation taxonomy defined in FTR-PROJECTED-FRAME-COLUMN-SEMANTICS-P5; the step does not introduce a parallel role vocabulary. A new shared resolver module (spreadsheet_handling.domain.column_roles) is the single source of truth for role detection in the current code base; the future targeting implementation slice (FTR-DYNAMIC-VIEW-COLUMN-TARGETING-IMPL-P5) will reuse it.

  • The worldbuilding consumer migrated its two projection plugins (build_story_cast_matrix_view, build_story_cast_matrix_payload) to project_by_role at all 10 current call sites (5 outbound
    5 inbound). The plugin functions remain importable and behavior-compatible for one release cycle; per-surface rollback is a one-line YAML edit (outbound: restore the *_matrix_enriched join_frames output: name and re-introduce the plugin step; inbound: restore the *_matrix_payload consumer matrix: name and re-introduce the plugin step).

  • add_validations rule targets now support role-based column targeting for dynamic workbook views. A target can specify roles: [matrix_value] (or row_identity / display_helper) and the step expands the target to the matching concrete columns using the shared column-role resolver. This is intended to replace consumer-side plugin fan-out such as add_from_legend_constraints_for_matrix for dynamic matrix columns. The first slice covers the validation / constraint metadata path; broader presentation-target surfaces remain deferred.

  • FK Helper Slice 2 (v1 retirement): configure_fk_helpers now writes only the durable v2 relation model under _meta.helper_policies.fk.relations; the legacy v1 per-target dict (_meta.helper_policies.fk.<target_key>) is no longer written. Those v2 relations are now durable — the persistence boundary no longer prunes relations by produced_by.step, so they survive into the sidecar / workbook and drive reverse-pipeline cleanup without a v1 dict. produced_by is retained on each relation as provenance and as the cross-producer conflict key. The Dino-shaped replay failure that motivated pruning configure relations is now contained at the materialisation point: enrich_helpers preserves the source frame’s column flatness and skips relations whose target frame is absent, so a durable relation can no longer turn a flat frame into a non-flat one or crash on a missing target. Public YAML / CLI surface is unchanged; the persisted _meta shape shrinks (no v1 dict). Migration: an artifact produced by a pre-Slice-2 run (v1 dict kept, configure v2 pruned) that is reimported without a fresh forward run has no v2 cleanup anchor unless it also recorded sheets.<frame>.helper_columns; re-run the forward pipeline once to re-bootstrap the durable v2 relation. See audit/fk_helper_slice2_v1_retirement_review.adoc.

2.4. Schema maintenance CLI

  • New CLI entry point sheets-schema-maintain performs explicit one-shot schema column maintenance over loaded Frames. The supported operations are add_column, drop_column, rename_column, and reorder_columns.

  • The command is dry-run by default. Dry-run output is routed to the new output-only saver kind discard, which accepts the final Frames payload but writes no artifact. User-selected output writes require --write; write mode uses the caller-provided --out-kind and --out-path.

  • Schema maintenance reports are emitted outside Frames and outside _meta. The report is printed as JSON to stdout by default, or written to the path supplied with --report.

  • Known limitations for this maintenance slice: there is no normal sheets-run YAML step and no public pipeline registry step; this is not a generic migration framework; workbook-header inference and dynamic projection schema handling are out of scope; FK relation drops remain blocked. (The earlier limitation about residual v1 _meta.helper_policies.fk per-target entries being blocked no longer applies: FK Helper Slice 2 retired the v1 producer write, so no such entry is produced; a v1 dict in a legacy sidecar is inert and passes through unchanged.)

2.5. CLI surface cleanup

  • Removed the placeholder example console scripts sheets-example-json-to-xlsx and sheets-example-xlsx-to-json. The maintained public CLI surface is now sheets-run plus the dedicated sheets-schema-maintain command.

2.6. Known limitations

  • Still true from 0.2.0: visible spreadsheet payload is a string substrate. Numeric, boolean, and date/time values in workbook cells are read and written as text by both the XLSX and ODS backends; type information present in the carrier is not preserved by default. A JSON value such as {"sequence_no": 1} may therefore round-trip through a workbook as {"sequence_no": "1"}. Typed roundtrip is not configured through workbook metadata: there is no cell_codecs metadata family (it is retired), and the string substrate is intentional. The decision and documented migration paths are recorded in ADR-VISIBLE-CELL-TYPING-STRING-SUBSTRATE (docs/technical_model/ch03_architecture_decisions/); the closing of FTR-VISIBLE-CELL-TYPING-STRATEGY-P5 is the explicit project-level position behind this behaviour.

3. 0.2.0 (released)

These notes describe the intended 0.2.0 release line relative to v0.1.0b6, the latest beta tag at the time this draft was written.

0.2.0 is still early-stage, pre-1.0 software. The release is not a promise of long-term API or YAML stability. If cut from this line, however, it is no longer positioned as a pure beta prototype: the core architecture, public documentation entry points, and release process are now stable enough for careful early adopters who are willing to follow the documented migration notes.

3.1. Highlights

  • Repeated export/reimport/promote cycles are stable: the orchestrator now projects the runtime _meta onto a persistable contract before any backend writes, so runtime-produced FK-helper v2 relations no longer leak into persisted sidecars and replay as stale policy on the next run. This closes the Frame 'groups' must have flat columns failure that the worldbuilding adoption surfaced. The boundary is intentionally narrow and post-pipeline: it prevents new contamination on every successful run, but a _meta.yaml already promoted from a pre-fix run may still need a one-time cleanup of its helper_policies.fk.relations entries before the next export can succeed. A complete _meta lifecycle inventory and load-time sanitizer are deferred to post-release follow-ups (FTR-FK-HELPER-POLICY-LIFECYCLE-P4A, FTR-META-LIFECYCLE-INVENTORY-P5).

  • ODS reimport is robust against sheet-wide formatting fillers. Workbooks edited with whole-sheet selections (e.g. Ctrl+A + format change in LibreOffice Calc) no longer trigger uncontrolled allocation in the ODS parser, and a typed SpreadsheetTooLargeError surfaces before unbounded growth when an input declares implausible dimensions.

  • FK-helper behavior has moved from convention-driven primitive inference to explicit relation policy. Pipelines should now configure or infer FK relation policy before running FK-helper primitives.

  • Public documentation entry points were clarified: the README, Pages root, release notes, user guide, and demo walkthrough paths now form an intent-based user journey rather than a collection of repository paths.

  • Release-readiness tooling was tightened with read-only checks for release branch state, README link versioning, Pages publication structure, and cross-repo release status.

  • The semantic model documentation now gives maintainers and agents a shared vocabulary for metadata meaning, lifecycle state, registry authority, and FK-helper contract review.

3.2. User-facing changes

  • Ctrl+C during sheets-run now exits cleanly with Interrupted by user. on stderr and a non-zero exit code (130, the POSIX SIGINT convention), in place of a raw Python traceback. --debug or -vv still shows the full traceback for debugging. The installed entry point is now routed through the existing run_cli wrapper, so the previously silent Error: …​ short-message path also reaches real users; reinstall with make setup or pip install -e . to regenerate .venv/bin/sheets-run.

  • The core README now directs readers to the maintained demo, the latest user guide, and the version archive with clearer intent labels.

  • The Pages root now acts as a version archive with links to core release notes, the user guide, and the maintained demo walkthrough.

  • Release-bound README links are guarded so PyPI and other frozen release contexts use /versions/<tag>/…​ documentation links instead of drifting to /latest/…​.

  • The user-guide transformation catalog was updated for the current FK-helper model, including the infer_fk_relations configuration step and policy-driven FK-helper primitives.

  • Canonical workbook reimport pipelines that declare helper cleanup now remove visible FK helper columns again after the persistence boundary strips transient _meta.derived provenance.

3.3. Transformation and pipeline changes

  • Added infer_fk_relations as an explicit configuration step. It can inspect current frames using a bounded naming-convention mode and write resolved FK relation policy to _meta.helper_policies.fk.

  • configure_fk_helpers remains the explicit/manual FK policy path. targets: "auto" was removed from this step; use infer_fk_relations when heuristic relation discovery is wanted.

  • FK-helper primitives now consume v2 relation policy under _meta.helper_policies.fk (schema_version: 2) instead of inferring relation identity from frame, table, or column names.

  • add_fk_helpers writes derived helper provenance that includes target_key, so later validation and cleanup can use the declared target primary-key column.

  • remove_fk_helpers, reorder_fk_helpers, and FK-helper validation now use policy and/or derived provenance. Missing required policy or provenance is a clear error rather than a silent prefix-based fallback.

  • apply_derived_column_policy …​ policy: drop now falls back to durable workbook-view helper metadata (_meta.sheets.<frame>.helper_columns) when transient _meta.derived.sheets.<frame>.helper_columns is absent after a fresh workbook reimport.

  • validate_references gained a no_helper_columns assertion rule. Use it after cleanup in reimport pipelines to report helper columns that would otherwise reach canonical output.

3.4. Spreadsheet backends and roundtrip behavior

  • The FK column wire format, such as id_(<target>), remains valid for spreadsheet roundtrips. The change is where relation meaning is resolved: configuration steps may use the convention, but primitive FK-helper steps do not infer relation identity from it.

  • No broad new spreadsheet backend capability is introduced in this release draft. XLSX remains the primary spreadsheet backend, and ODS/Calc remains the second backend used to prove the spreadsheet contract.

  • Roundtrip-sensitive helper behavior is now more explicit because helper cleanup and validation rely on declared policy/provenance rather than hidden name-pattern recovery.

  • The orchestrator now owns a narrow persistence boundary that projects runtime meta onto a carrier-neutral persistable contract before save. Top-level derived and _*-prefixed keys are dropped, and FK-helper v2 relation entries under helper_policies.fk.relations are removed when their produced_by.step is configure_fk_helpers. The boundary applies to every output kind (JSON/YAML/XML/CSV directories and XLSX/ODS); the projection is the same for all carriers, with spreadsheet backends layering rendering on top. The pipeline.runner.run_app entry point is a thin adapter over orchestrate and inherits the same boundary, so there is exactly one load/step/save path in the project. See docs/semantic_model/08_lifecycle_and_update_semantics.adoc for the boundary contract, the post-pipeline / write-side scope, and the explicitly deferred follow-ups (FTR-FK-HELPER-POLICY-LIFECYCLE-P4A, FTR-META-LIFECYCLE-INVENTORY-P5).

  • The ODS parser no longer materializes empty cells declared via number-columns-repeated / number-rows-repeated. This neutralizes the common LibreOffice "select all + apply style" carrier pattern, which previously expanded a single empty styled cell into millions of dict entries and could exhaust process memory on real-world inputs.

  • parse_workbook accepts a new keyword argument limits=ParserLimits(…​) for defense-in-depth caps on parsed rows, columns, and materialized cells. Exceeding a limit raises the typed SpreadsheetTooLargeError (re-exported from spreadsheet_handling.io_backends.parser_limits) instead of a raw MemoryError. Defaults align with the spreadsheet maxima (1,048,576 rows × 16,384 columns) with a 10,000,000 cell ceiling per sheet.

3.5. Documentation and demo

  • Public documentation entry points were realigned around the README, Pages root, user guide, release notes, and demo walkthroughs.

  • The maintained demo/tutorial path was realigned with explicit FK-helper policy semantics.

  • The semantic model documentation was added under docs/semantic_model/, including the problem statement, semantic sets and lifecycle model, registry role, adoption strategy, and FK-helper contract matrix.

  • The project evolution narrative was updated so future maintainers and agents can understand the release, FK-helper, registry, and semantic-model phases without reading every historical FTR.

3.6. Migration notes

  • Pipelines that relied on configure_fk_helpers with targets: "auto" must switch to an explicit infer_fk_relations step before FK-helper primitives, or provide explicit/manual relation policy through configure_fk_helpers.

  • Pipelines that previously expected add_fk_helpers to discover FK relations implicitly from column names must run a configuration step first.

  • Pipelines that relied on prefix fallback during remove_fk_helpers should preserve the derived helper provenance written by add_fk_helpers or provide explicit policy. Recovery from externally edited workbooks without provenance is not part of the normal primitive behavior.

  • FK relation policy now uses the v2 relation-oriented shape under the existing _meta.helper_policies.fk root. The relation shape includes schema_version: 2, relations, source_frame, source_column, target_frame, mandatory target_key, helper fields/columns, and produced_by metadata.

  • The old id_(<target>) FK column convention is not removed. It is still the cell-level wire format and may be used by infer_fk_relations; it is no longer the hidden authority inside primitive FK-helper execution.

3.7. Internal architecture and maintainability

  • Registry contract lifecycle guidance now distinguishes current state, target state, and transition bridges so registry entries can describe migrations without overstating runtime truth.

  • Registry artifacts were relocated to root-level registries/ paths while documentation keeps the reviewed registry contract context.

  • Release tooling now includes read-only helpers for release branch validation, Pages publication checks, cross-repo release status, and README link versioning.

  • GitHub Actions workflow permissions were tightened to minimal defaults with job-level overrides where required.

  • The FK-helper semantic contract matrix and guards reduce the chance that future refactors reintroduce primitive inference or stale registry wording.

3.8. Known limitations

  • 0.2.0 remains pre-1.0. Public behavior is more coherent than the beta prototype line, but compatibility promises are intentionally limited.

  • Historical beta-by-beta release notes are not reconstructed here. This page focuses on changes since v0.1.0b6.

  • Some semantic-model adoption work is intentionally documentation-first. Future transformation families still need their own adoption slices.

  • REVIEW-002 residual maintainability items remain tracked outside these release notes. They are not treated as release blockers unless later review promotes them to 0.2.0 scope.

  • The FK-helper policy model does not yet claim to cover composite keys, generic relation modeling, or every possible recovery flow for externally edited workbooks.
